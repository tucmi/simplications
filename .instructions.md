# Simplications Development Instructions

## Project Overview

**Simplications** is a Flutter smart-home privacy risk assessment tool that helps households evaluate and understand the privacy and security risks of their connected devices. Users answer structured questionnaires about devices, receive risk scores, and get tailored mitigation recommendations.

- **Target platforms:** Android, iOS, Web, Windows, macOS, Linux
- **Supported languages:** German (de), English (en), Czech (cs), Polish (pl), French (fr), Dutch (nl), Danish (da)
- **Key features:** Device questionnaire wizard, risk scoring with penalties, household-level aggregation, PDF/text export
- **Repository:** https://github.com/tucmi/simplications

## Tech Stack

- **Framework:** Flutter 3.11.5+, Dart 3.1.0+
- **Build system:** Gradle (Android), Xcode (iOS), CMake (Linux/macOS/Windows)
- **Key packages:** `pdf: ^3.11.3`, `share_plus: ^11.0.0`, custom localization
- **Versioning:** Semantic versioning (`major.minor.patch+buildNumber`) in `pubspec.yaml`

## Development Guidelines

### Code style and quality
- Run `flutter analyze` before committing — all issues must be resolved
- Follow Dart style guide; use meaningful variable and function names
- Prefer immutable data classes (use `final` fields)
- Add docstring comments to public classes and methods explaining purpose and key behavior

### Localization
- All UI strings must use `AppLocalizations` (generated from `lib/l10n/app_localizations.dart`)
- When adding new user-facing text:
  1. Add German text to the `_deToEn` map in `lib/data/catalog_data.dart` or directly in the UI
  2. Use `AppLocalizations` instance to retrieve the localized value
  3. Run `flutter gen-l10n` to regenerate localizations
  4. Verify translations exist in all 7 supported locales before merging
- Special characters: Use only ASCII-safe characters or ensure PDF fonts support them (see below)

### PDF export
- All text rendered to PDF must use characters covered by Helvetica (Latin-1, ISO 8859-1)
- Avoid en-dashes (`–`), em-dashes (`—`), and non-Latin accented characters in strings used in PDF export
- If internationalization requires unsupported characters, consider embedding a Unicode font (e.g., `Roboto`)

### Testing
- Run `flutter test` before opening a PR — all tests must pass
- Write widget tests for complex UI components (dialogs, forms, risk displays)
- Test localization changes with at least two locales (preferably one with special characters)

### Commits and PRs
- Use conventional commit format: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`
- Reference related issues with `Fixes #…` or `Closes #…` in PR descriptions
- Split logical changes into separate commits; avoid unrelated refactors in feature PRs
- All PRs must pass CI (analyze, build APK release)

## Version Management and Build Numbers

### Versioning model
- **Format:** `X.Y.Z+N` in `pubspec.yaml` (e.g., `1.2.0+42`)
  - `X.Y.Z`: Semantic version (public version name)
  - `N`: Build/internal number (Android `versionCode`, iOS `CFBundleVersion`)

### Build number increment workflow
**Every completed task/PR should increment the build number by 1:**

1. After merging a feature, fix, or refactor to `main`:
   - Edit `pubspec.yaml` and bump the build number: `version: X.Y.Z+N` → `version: X.Y.Z+(N+1)`
   - Example: `1.0.0+1` → `1.0.0+2`
   - Do not change the semantic version unless explicitly planning a release

2. When releasing to stores:
   - Bump semantic version (e.g., `1.0.0` → `1.1.0` for feature release, `1.1.1` for hotfix)
   - Commit: `git commit -m "chore: bump version to X.Y.Z"`
   - Tag: `git tag vX.Y.Z` (tag format does not include build number)
   - Push with tags: `git push origin main --tags`
   - CI workflow (on `v*` tag) will validate pubspec version matches tag and create GitHub Release

### Example increment sequence
```
Task 1: Add device filter feature     → version: 1.0.0+2 (merged, bumped)
Task 2: Fix PDF export bug            → version: 1.0.0+3 (merged, bumped)
Task 3: Localize to French            → version: 1.0.0+4 (merged, bumped)
Release 1.1.0: Prepare release        → version: 1.1.0+4 (semantic bump), tag v1.1.0
Task 4: Refactor risk scoring         → version: 1.1.0+5 (merged, bumped)
```

## Folder Structure

- **`lib/`**: Dart source code
  - `main.dart`: App entry point
  - `data/catalog_data.dart`: Device catalog, recommendations, translations
  - `models/`: Core data models (Device, Room, risk scoring logic)
  - `screens/`: UI screens (Welcome, Room/Device Selection, Questionnaire, Summary)
  - `widgets/`: Reusable UI components
  - `l10n/`: Localization utilities
- **`test/`**: Widget and unit tests
- **`android/`, `ios/`, `web/`, `linux/`, `windows/`, `macos/`**: Platform-specific code
- **`.github/workflows/`**: CI/CD pipelines
- **`.github/ISSUE_TEMPLATE/`**: Issue and PR templates

## Key Codebase Knowledge

- **Risk scoring:** Defined in `lib/models/device.dart`; each device receives a score based on security/privacy penalties; overall household score is the mean of device scores
- **Device types:** Categorized in `lib/data/catalog_data.dart` (e.g., Smartphone, SmartSpeaker, SmartTV); each has tailored questionnaire
- **Questionnaire flow:** Users select devices → device-type-specific questions → summary with scores and recommendations
- **Exports:** PDF (styled, multi-page) and plain text; generated on-the-fly from `_SummaryReport` data
- **Localization:** Bidirectional (German ↔ English) string maps in `catalog_data.dart`; generated localizations extend this

## CI/CD

- **`check.yml`**: Runs on every push to any branch
  - Builds APK release: `flutter build apk --release`
  - Uploads APK artifact for download
- **Release workflow** (on `v*` tags): Validates version match, builds, creates GitHub Release (to be implemented)
